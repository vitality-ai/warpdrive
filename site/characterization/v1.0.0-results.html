Why content-dependent placement

Object stores have always treated a stored object as an opaque blob: whatever bytes a client sends get striped, erasure-coded, and handed back whole on read. That's fine for archival and file uploads, but it's a bad fit once an analytical query engine or a vector-index search is the actual client. A Parquet file has column chunks. A Lance index has per-partition structure. A query that only needs one column, or one nprobe's worth of partitions, still has to pay for reconstructing the entire object on a plain erasure-coded store, because the store has no concept of where the part it needs actually lives.

WarpDrive's content-dependent placement lets a bucket opt a workload's own internal byte layout into how it gets striped, so a query can touch only the stripes that actually cover the bytes it needs. The catch is that this can't be a blind optimization: a bad packing decision must never risk availability, so every packer reports its own storage overhead and the system falls back to plain whole-object storage automatically if that overhead crosses a configured threshold. The two results below are the same mechanism applied to two different workloads, an analytical SQL engine and a vector search engine, to check the benefit holds for more than one shape of structure, not just one convenient case.

Analytical SQL · Official TPC-H via DuckDB, pushdown

DuckDB's tpch extension generates the official TPC-H dataset (dbgen, sf=1 → 6,001,215 lineitem rows) and exposes the official 22 queries verbatim. Q1 and Q6 are the only two that touch solely lineitem. The exported Parquet file was physically sorted by l_shipdate before upload, a standard clustering technique (the same idea as Databricks' Z-ORDER), which is what makes Q6's one-year date predicate actually prunable via row-group min/max statistics.

Q6 (selective) vs. Q1 (control), median latency

Packed-bucket cost scales down with query selectivity (a stripe boundary to skip past). Plain-bucket cost stays flat regardless of selectivity (no sub-object boundary to exploit at all). Q1 has no plain bar: its near-full-table-scan plain-bucket cost was already evidenced per-request elsewhere and repeating it here is what made an earlier run impractically slow.

Vector Search · Lance IVF_PQ, content-dependent placement

Lance's own object_store::aws client pointed at two WarpDrive buckets holding the same dataset, same index, same unmodified query engine. One bucket stored plain (whole-object erasure coding), the other configured to use IvfCentroidPacker, which groups IVF partitions by k-means cluster id and bin-packs within each cluster.

Methodology notes and caveats, stated directly:
  • All results use the dev-loop default RS(3,2) (3 data + 2 parity shards), not Fusion's RS(9,6). Re-running at RS(9,6) is the natural next validation step.
  • All measurements are from a local multi-process cluster on one machine (gRPC calls between nodes, disk I/O per node), not yet a multi-VM/cross-datacenter run.
  • No MinIO comparison yet, tracked as follow-up work.
  • SIFT1M-small, not full SIFT1M, the 10k-vector subset, not the full 1M-vector corpus.
  • Every number above came from a script that also independently verifies correctness (byte-identical round-trip, recall@10 against ground truth, or exact result-value equality) in the same run that produced the timing.
