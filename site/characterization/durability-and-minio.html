Why this exists

A direct question — "why didn't chaos testing catch this?" — surfaced that WarpDrive's write paths, single-node and cluster alike, never called fsync anywhere. Every acknowledged write was only as durable as the OS page cache until some unrelated future flush happened to write it back. A naive per-write fix measured at an 82-89% throughput cost, bad enough to drop below MinIO's own ceiling — rejected rather than shipped. The fix that actually shipped is a group-commit design: concurrent writers collapse into one real fsync per batch instead of each paying their own, closing the durability gap without a fixed timer or an ack-before-durable race window.

Partway through verifying this on GCP, the account's hardware (e2-small + pd-standard, the slowest disk tier GCP offers) turned out to be hiding something: vmstat showed MinIO doing real I/O wait, not CPU work, meaning the original comparison was partly measuring a weak disk, not either server's actual ceiling. Upgrading to local NVMe SSD and re-running closed that gap — and separately, a direct challenge to the benchmark methodology ("why are you driving MinIO and WarpDrive with two different client tools?") led to patching the open-source warp client so the exact same binary could drive both.

1. The cost of real durability — and what group-commit recovers

Single coordinator, concurrency=64, RS(3,2), 5-node cluster. Same client tool and same hardware across all three bars — only whether/how each write is fsync'd changes.

Single coordinator, req/s (higher is better)

No-fsync is fast but unsafe — an acknowledged write can be lost on a kernel panic or power loss before the page cache flushes. A naive per-write fsync closes that gap but costs 82-89% of throughput. Group-commit recovers most of the gap by batching concurrent writers into one real fsync per batch, with durability fully restored.

2. Hardware was hiding the real comparison

Each system compared only to itself, same client tool and same method on both sides — this isolates what the hardware upgrade alone did, before the client-harness fix below. 5-node aggregate throughput, concurrency=640 total.

5-node aggregate req/s, old vs. new hardware (log scale)

vmstat on a MinIO node during the old-hardware run showed real I/O wait (16-28%), not CPU saturation — pd-standard was the bottleneck, not either server's actual logic. Swapping to local NVMe SSD alone, no code changes, moved both systems by a similar multiple.

3. Final comparison: one client, both servers, new hardware

warp (MinIO's own benchmark tool) cannot address WarpDrive's real distributed path out of the box — its client library explicitly rejects a path-prefixed endpoint, and WarpDrive's actual erasure-coded path only exists at a non-root path. Patched the client (~10 lines, no changes to WarpDrive itself) so the identical binary drives both servers, with real SigV4 signing verified correct on both sides, zero errors in every run.

Methodology notes and caveats, stated directly:
  • All results use RS(3,2) (3 data + 2 parity shards), the dev-loop default, not Fusion's RS(9,6).
  • Measured on a real 5-node GCP cluster (n2-standard-2, local NVMe SSD), not a local-machine simulation — the account's global vCPU cap ruled out a larger per-node instance size, so single-node throughput here is capped by 2 vCPUs doing real erasure-coding + fan-out + fsync work, confirmed via vmstat showing CPU, not disk, as the limit at that point.
  • Section 1's numbers are from the prior (smaller, disk-bound) hardware generation, kept as-is because they isolate the durability-mode comparison specifically — re-running them on the new hardware is natural follow-up work.
  • MinIO ran with its own default erasure-coding parity for a 5-drive single pool; both systems' writes were fsync'd durably in every comparison on this page.
  • Every number above came from a real run against live servers (local or GCP), not estimated or extrapolated.
