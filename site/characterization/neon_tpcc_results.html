TPS — Total & Per-Tenant vs Tenant Count

All T endpoints run sysbench in parallel, so total TPS should ideally grow linearly with T. It doesn't — all endpoints share one pageserver, which simultaneously handles cold-start layer downloads, 4MB checkpoints, and eviction for every timeline at once. TPS/tenant drops 7× from T=1 to T=8 as the pageserver saturates. At T=16 the system collapses entirely: 4 of the 16 endpoints require more than 120s just to warm up their first page (192s avg latency), contributing zero transactions. Total TPS falls from 38.9 (T=8) to 4.1 (T=16) — a single pageserver simply cannot absorb the cold-start download pressure of 16 concurrent timelines.

GET Amplification — Delta vs Image vs Tenant Count

GETs grow super-linearly: 68 → 109 → 954 → 2,981 (44× from T=1 to T=16). Two sources: startup GETs scale roughly linearly (each timeline re-downloads its working set on cold start) and eviction GETs grow much faster (more tenants → more I/O competition → higher eviction rate → more on-demand re-fetches mid-run). Delta GETs account for ~85% across all T — each delta GET requires k sequential round-trips to WarpDrive to reconstruct a page from the delta chain. This is the dominant read cost that WarpDrive's co-located slabs are designed to eliminate.

PUTs & DELETE_OBJECTS vs Tenant Count

PUTs peak at T=4 (1,123), then drop at T=8 and T=16 — not because fewer checkpoints fire, but because lower TPS means less WAL generated per unit time, so fewer 4MB thresholds are reached in 120s. At T=16 the system is so congested that most endpoints produce nearly no new WAL. DELETE_OBJECTS grows with T — compaction GC sweeps batch-delete superseded delta layers. Both are billed at the write tier ($0.005/1k), making DELETE_OBJECTS disproportionately expensive relative to the work done.

Latency (avg & p95) vs Tenant Count

Average latency rises sharply with tenant count as the pageserver becomes congested. The p95 at T=8 (≈5s) reflects worst-case cold-start download blocking: a transaction stalls while the pageserver fetches a delta chain from WarpDrive before it can serve the page. At T=16, p95 hits the 100s cap — 4 of the 16 endpoints couldn't complete a single transaction within the 120s window, spending the entire run waiting on page downloads from an overloaded pageserver.

Cold start: every run wipes local layer files and restarts the pageserver, so each endpoint must re-download its working set from WarpDrive on first page access. Startup GETs are purely cold reads; benchmark GETs are eviction-driven mid-run re-fetches.

Super-linear GET growth (68 → 109 → 442 → 768 for T=1,4,8,16): more tenants means more timelines competing for pageserver I/O, higher eviction pressure per timeline, and cold-start downloads that pile up linearly across timelines. Delta GETs account for ~89% across all T — each delta GET requires k independent WarpDrive round-trips to reconstruct a page.

On a flat immutable object store, S3 forces the full PUT → evict → DELETE_OBJECTS/GET cycle. WarpDrive's co-located mutable slabs collapse this: append-in-place eliminates the GC cycle, and cold reads resolve in one batched I/O rather than k sequential round-trips.

Delta fraction ≈85% across all T — page reconstruction cost dominates, not image warmup.

Super-linear growth is explained by ρ rising with T: multi-tenant eviction pressure increases the miss rate faster than T grows. GET:PUT ratio rises from 0.23 (T=1) to 3.51 (T=16) — the system spends 3.5× more on reads than writes at full load.

DELETE_OBJECTS scales with compaction GC frequency — write-tier billed, 3→3→6→12 across T=1,4,8,16. WarpDrive mutable slabs eliminate this entirely.
